## 2. 产品定位与版本范围

### 2.1 一句话定位

LifeOps Travel Agent 是面向普通用户的出行与生活路线规划 AI Agent，能够基于用户自然语言需求、实时工具结果、预算约束和个人偏好，生成可执行、可追溯、可确认的出行计划。

这里的“公司级应用”指产品工程质量、稳定性、可观测性、安全性和测试标准达到公司级交付要求；不代表产品定位变成企业内部流程系统。

### 2.2 产品背景

普通人在周末出游、城市一日游、跨城短途、约会、餐饮、办事和轻量旅行场景中，往往需要同时查询天气、地点、路线、预算、营业信息、交通时间和个人偏好。传统方式依赖用户在多个 App 间反复切换，耗时高，且容易出现路线不顺、预算失控、天气风险未考虑、推荐缺少依据等问题。

当前 LifeOps 已具备 Agent 工作流、工具调用、trace 记录、反馈画像、日历导出和 API 服务能力。MVP 的目标不是增加复杂内部管理业务，而是把普通人出行规划做成一个稳定、可测试、可上线、可演示的公司级 AI 应用。

### 2.3 MVP 范围

MVP 覆盖以下场景：

- 城市一日游 / 半日游规划
- 跨城短途出行规划
- 周末轻旅行规划
- 餐饮与约会路线规划
- 多地点办事顺路规划
- 天气、地点、路线、预算、网页搜索工具调用
- 计划生成、风险提示、工具证据展示
- 用户确认后导出日历 ICS
- 历史记录、trace、反馈收集和用户偏好更新

### 2.4 非 MVP 范围

以下能力暂不进入 MVP：

- 自动订票
- 自动付款
- 自动提交订单
- 自动发送外部邮件或 IM 消息
- 酒店/机票实时交易闭环
- 下单、付款、外部写入或管理审批流程
- 多租户管理后台
- 移动端原生 App
- 语音输入、图片理解

## 3. 产品目标与成功指标

### 3.1 产品目标

- 让普通用户通过自然语言快速生成可执行的出行计划。
- 让计划结果具备工具依据、预算估算和风险提示。
- 让高风险或写入型动作必须经过用户确认。
- 让每次 AI 规划过程可追踪、可复盘、可测试。
- 让产品具备公司级应用所需的接口契约、日志、评估和上线检查。

### 3.2 用户痛点

- 出行计划需要查天气、地图、攻略、餐饮、预算，信息分散。
- AI 推荐容易编造地点、路线、价格或营业信息。
- 用户不知道哪些信息来自工具，哪些只是模型建议。
- 路线容易太赶、折返多，和用户偏好不匹配。
- 工具失败时用户不知道哪些结论不可靠。

### 3.3 业务目标

- 降低用户制定出行计划的时间。
- 提升计划可执行性和用户采纳率。
- 沉淀用户偏好、反馈和 Bad Case。
- 建立可演示、可测试、可上线的 AI Agent 应用样板。

### 3.4 成功指标

| 指标 | 定义 | MVP 目标 |
|---|---|---|
| 计划生成成功率 | `/app/runs/plan` 返回成功，且响应通过 schema 校验 | >= 95% |
| 工具证据覆盖率 | 涉及天气、地点、路线、搜索时，输出包含工具结果或失败说明 | >= 90% |
| 用户采纳率 | 用户点击采纳、导出日历或确认方案 | >= 60% |
| 工具调用成功率 | 工具返回成功且字段完整 | >= 95% |
| 高风险误执行次数 | 未经确认执行写操作的次数 | 0 |
| 首个流式事件延迟 | 用户提交后第一个 SSE 事件返回时间 | <= 2 秒 |
| 完整计划响应时间 | 从提交到最终计划生成 | <= 20 秒 |
| 单次请求成本 | 单次 Agent 运行的模型成本估算 | <= 0.2 元 |

## 5. 核心场景与用户流程

### 5.1 正常流程

1. 用户输入出行或生活路线需求。
2. 系统抽取时间、地点、预算、偏好、限制条件。
3. 系统读取用户本人偏好。
4. 系统调用天气、地点、路线、预算、网页搜索工具。
5. Agent 生成候选地点和候选计划并评分。
6. Agent 进行风险检查和反思修正。
7. 系统输出结构化计划、工具依据、风险提示和待确认动作。
8. 用户确认是否导出日历。
9. 系统保存历史记录、trace 和用户反馈。

### 5.2 信息不足流程

触发条件：

- 缺少出发地且影响路线判断
- 缺少目标城市或地点
- 时间表达无法解析
- 预算严重缺失且影响判断

处理方式：

- Agent 不直接生成完整计划。
- 返回最多 3 个澄清问题。
- 已明确的信息仍保留在上下文中。

### 5.3 工具失败流程

触发条件：

- 天气、路线、地点、搜索、预算工具超时或返回错误。

处理方式：

- 标注失败工具名称。
- 不使用失败工具的信息生成事实结论。
- 可输出降级建议，但必须标注低置信度。
- 保存失败日志和 trace。

### 5.4 信息冲突流程

触发条件：

- 地图、搜索、天气等工具结果互相冲突。
- 用户需求与工具结果明显不一致，例如预算过低、时间过短、地点无法定位。

处理方式：

- 优先使用结构化工具结果。
- 输出冲突说明。
- 将相关结论标记为“建议”或“需要用户确认”。

## 6. AI 能力与边界

### 6.1 AI 角色定位

AI 是普通人的出行规划助手，负责理解需求、调用工具、生成建议、提示风险和记录过程。

AI 不是票务代理、支付工具、法务顾问、医疗顾问，也不是自动执行系统。

### 6.2 AI 要完成的任务

- 自然语言意图识别
- 约束抽取
- 日期解析
- 用户偏好读取
- 天气、地点、路线、预算、网页搜索工具调用
- 多候选方案生成与评分
- 风险检查
- 计划反思与重规划
- 日历导出草稿生成
- 用户反馈总结与偏好更新

### 6.3 AI 不应该做什么

- 不编造价格、路线、天气、营业时间或地点信息。
- 不访问其他用户隐私数据。
- 不自动订票、付款、下单或发送外部消息。
- 不删除或修改系统审计数据。
- 不输出法律、医疗、投资等专业建议。
- 不把工具失败结果伪装成成功。

### 6.4 拒答或转人工场景

以下场景必须拒答或给出安全提示：

- 用户要求伪造凭证、逃票、欺诈或违法。
- 用户要求查看其他用户隐私数据。
- 用户要求自动付款或下单。
- 用户要求删除审计日志。
- 用户输入包含违法、欺诈或明显不安全意图。

### 6.5 不确定性表达规则

- 来自工具的事实：正常陈述，并附工具来源或链接。
- 来自模型推理的内容：必须标注“建议”“估算”或“假设”。
- 搜索不到有效信息：必须说明“未找到明确公开信息”。
- 工具失败：必须说明失败原因和影响范围。
- 信息不足：必须先澄清，不生成伪完整计划。

### 7.4 输出质量要求

合格输出必须包含：

- 任务理解
- 关键约束
- 时间安排
- 地点或路线
- 预算估算
- 工具证据或无证据说明
- 风险提示
- 待确认动作

缺少任一关键字段则判定为输出不合格。

### 7.5 错误输出示例

```text
你可以随便去，应该都很便宜。
```

错误原因：

- 编造价格或预算判断。
- 没有路线和时间安排。
- 没有工具依据。
- 没有风险提示。

### 7.6 理想输出示例

```text
推荐方案：周三 08:30 从杭州出发，10:00 到达上海，上午安排博物馆，下午安排外滩和咖啡休息，19:00 返程。

预算估算：交通约 320 元，餐饮约 180 元，市内交通约 80 元，总计约 580 元，低于 1200 元预算。

工具依据：天气工具显示上海当天可能有降雨；路线工具估算杭州到上海约 1.5 小时；地点工具返回外滩和博物馆可定位。

风险提示：降雨会影响外滩步行体验，建议预留 30 分钟缓冲，并准备室内备选。

待确认动作：是否导出 ICS 日历文件？
```

## 8. 数据来源与工具证据方案

### 8.1 数据来源边界

MVP 的事实依据来自实时工具、公开信息工具和用户本人数据：

- 天气工具
- 地点工具
- 路线工具
- 预算工具
- 公共网页搜索工具
- 用户本人历史反馈和偏好

### 8.2 工具证据展示规则

涉及事实判断时，应尽量展示：

- 工具名称
- 查询对象
- 结果摘要
- 链接或可定位信息
- 失败原因（如果失败）

不得把模型推理伪装成工具事实。

### 8.3 检索失败处理

如果公开网页搜索或地图工具未找到有效信息：

- 输出“未找到明确公开信息”或“地点暂无法确认”。
- 不生成确定性营业、票价或路线结论。
- 将相关建议标记为低置信度或需要用户确认。

## 9. Agent 与工具调用

### 9.1 Agent 工作流

```text
用户输入
-> 约束抽取
-> 日期解析
-> 用户记忆读取
-> 澄清判断
-> 工具路由
-> 天气/地点/路线/预算/搜索工具调用
-> 候选方案评分
-> 风险检查
-> 反思修正
-> 最终计划输出
-> trace 与历史记录保存
```

### 9.2 调用限制

- 单次任务最大工具调用次数：8 次。
- 单次任务最大 replan 次数：1 次。
- 单个工具超时时间：5 秒。
- Agent 总超时时间：20 秒。
- 超出限制后必须返回降级结果或失败说明。

### 9.3 工具列表

| 工具 | 用途 | 权限 | 失败处理 |
|---|---|---|---|
| 天气工具 | 查询目的地天气 | 自动只读 | 标记天气未知，不做天气确定判断 |
| 地点工具 | 查询 POI 和地址 | 自动只读 | 请求用户补充地点 |
| 路线工具 | 估算交通时间 | 自动只读 | 标记路线低置信度 |
| 预算工具 | 估算费用和预算风险 | 自动只读 | 输出预算未知 |
| 搜索工具 | 查询公开网页信息 | 自动只读 | 不引用搜索信息 |
| 记忆工具 | 读取用户偏好 | 本人只读 | 不使用历史偏好 |
| 日历工具 | 导出 ICS | 用户确认后执行 | 未确认不生成日历文件 |

### 9.4 需要用户确认的动作

以下动作必须二次确认：

- 导出日历 ICS
- 创建提醒
- 修改用户偏好
- 写入外部系统

MVP 仅支持“确认后导出 ICS”，其他写操作只生成草稿。

### 9.5 禁止调用的操作

- 自动付款
- 自动订票
- 自动下单
- 删除用户数据
- 删除审计日志
- 访问其他用户隐私数据

## 10. Prompt 与模型策略

### 10.1 System Prompt

```text
你是 LifeOps Travel Agent，一个普通人出行规划助手。
你必须基于用户输入、用户偏好和工具结果生成计划。
你不得编造价格、路线、天气、营业时间或地点信息。
涉及不确定信息时，必须说明不确定。
涉及写操作时，必须请求用户确认，不得自动执行。
```

### 10.2 Developer Prompt

```text
输出必须包含：任务理解、关键约束、推荐计划、预算估算、工具依据、风险提示、待确认动作。
实时信息必须来自工具结果。
如果缺少关键信息，最多提出 3 个澄清问题。
如果工具失败，必须说明失败工具和影响范围。
```

### 10.3 User Prompt 模板

```text
用户需求：{user_input}
默认城市：{default_city}
出发地：{origin_location}
用户偏好：{user_profile}
工具调用结果：{tool_results}
历史计划：{previous_result}

请生成普通人出行规划方案。
```

### 10.4 输出格式约束

- API 返回 JSON。
- 前端展示 Markdown。
- JSON 必须通过 schema 校验。
- Markdown 必须包含固定章节。
- 不允许只输出自然语言闲聊。

### 10.5 Prompt 版本管理

- 每个 Prompt 使用版本号，例如 `travel_planner_v1.0`。
- 每次运行记录 prompt_version、model、trace_id。
- Prompt 修改必须先通过回归测试集。
- Prompt 发布流程分为 dev、test、prod。

## 11. 模型与技术方案

### 11.1 模型选择

| 任务 | 模型策略 |
|---|---|
| 意图识别 | 轻量模型或规则 |
| 约束抽取 | 轻量模型或规则 |
| 最终计划生成 | 主力 Chat Model |
| 高风险复核 | 规则优先，必要时更强模型 |
| 用户偏好总结 | 轻量模型或规则 |

### 11.2 技术架构

- 前端：React
- 后端：FastAPI
- Agent 编排：LangGraph 风格工作流
- 主数据库：MVP 使用 SQLite，后续可升级 PostgreSQL
- 缓存：MVP 可选，后续可接 Redis
- 鉴权：MVP 可使用 mock 用户，后续接 JWT
- 部署：Docker + CI/CD
- 观测：结构化日志、trace、错误告警

### 11.3 模型调用要求

- 支持流式输出。
- 支持最多一次 replan。
- 支持结构化工具调用。
- 后端统一封装模型调用。
- 前端不得直接调用模型 API。

### 11.4 兜底策略

如果主模型不可用：

- 自动切换备用模型。
- 如果备用模型也失败，返回工具结果摘要和失败说明。
- 不允许返回伪造计划。

如果关键工具不可用：

- 禁用对应事实结论。
- 输出工具不可用说明。
- 将相关建议标记为低置信度。

## 12. 数据、日志与隐私

### 12.1 数据分类

| 数据类型 | 示例 | 处理方式 |
|---|---|---|
| 普通数据 | 城市、日期、预算 | 正常保存 |
| 个人信息 | 姓名、手机号、邮箱 | 脱敏保存 |
| 用户偏好 | 喜欢咖啡、讨厌排队 | 仅本人可读写 |
| 位置数据 | 出发地、目的地、当前位置 | 按最小必要原则保存 |
| 密钥数据 | API Key | 不入库、不入日志 |

### 12.2 日志留存

- trace 日志默认保留 90 天。
- 用户历史记录默认保留 180 天。
- 审计日志默认保留 1 年。
- 用户可申请删除个人历史记录。

### 12.3 脱敏规则

日志中不得明文保存：

- API Key
- 身份证号
- 手机号
- 邮箱
- 详细联系人信息

## 13. 埋点与运营指标

### 13.1 关键事件

| 事件 | 说明 |
|---|---|
| plan_start | 用户开始创建计划 |
| constraint_extracted | 约束抽取完成 |

### 14.2 自动化评估指标

| 指标 | 验收标准 |
|---|---|
| JSON schema 通过率 | >= 99% |

### 14.3 人工评审标准

每条样本按 1-5 分评分：

- 计划可执行性
- 路线合理性
- 工具依据准确性
- 风险提示完整性
- 输出清晰度

上线门槛：

- 各项平均分 >= 4.0
- P0 Bad Case = 0
- P1 Bad Case <= 3

### 14.4 功能验收

- 用户输入出行需求后，系统必须返回结构化计划。
- 涉及实时信息时，必须返回工具依据或明确说明未找到。
- 工具失败时，系统不能编造结果。
- 写操作确认前不得执行。
- 普通用户不能查看其他用户历史。
- 运营管理员操作必须留下审计日志。

## 16. 风险清单

| 风险 | 等级 | 应对 |
|---|---|---|
| 模型编造价格/路线/天气 | 高 | 工具结果优先，无工具依据不输出确定结论 |
| 工具失败导致错误计划 | 高 | 工具失败显式标注，禁止伪造 |
| 未经确认执行写操作 | 高 | 后端确认 token 校验 |
| 用户越权访问历史 | 高 | user_id 过滤 + 审计日志 |
| 成本失控 | 中 | 限制工具调用次数和模型 fallback |
| 延迟过高 | 中 | 流式输出、缓存、超时降级 |
| 用户不信任 AI | 中 | 展示来源、风险和不确定性 |
| 位置隐私泄露 | 中 | 最小化保存、脱敏日志、权限隔离 |

## 17. 结论

LifeOps Travel Agent 的价值不在于“多生成几段攻略文本”，而在于把 LLM 放进可控的出行规划流程中：用工具调用获取实时信息，用用户偏好提高个性化，用确认机制控制写操作风险，用 trace 和评估体系支撑上线质量。

MVP 应聚焦“普通人出行规划”这一核心场景，先证明 AI Agent 能在真实约束下生成可信、可追溯、可执行的计划，再逐步扩展到更丰富的生活规划场景。
